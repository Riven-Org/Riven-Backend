# S08.4 · Regression lock for all confirmed bugs

- **Epic:** E08 · Bug Memory & Regression Lock 2.0 (Phase 3: Core Features — MVP Hardening)
- **Priority:** P0 · **Effort:** 8 story points
- **Depends on:** S08.3
- **Repos:** backend
- **Suggested tech / approach:** Claude API test generation, dual-commit validation in sandbox

## Description

Every fixed bug gets a lock test (existing or generated). A lock is valid only if it fails on the buggy commit and passes on the fix.

## Acceptance criteria (story)

- [ ] Lock validation runs test on both commits automatically
- [ ] LLM-generated lock tests require human approval before activation
- [ ] Lock coverage % shown per module

## Tasks

### S08.4.1 · Lock model & validation workflow

- **Repo:** backend
- **Size:** M (S ≤ 1 day, M 2–3 days, L 4–5 days)
- **Depends on:** previous tasks in this story as needed
- **What to do:** Run on buggy + fixed commits.
- **Done when:** Invalid lock (passes on buggy) rejected

### S08.4.2 · LLM lock-test generator from repro

- **Repo:** backend
- **Size:** L (S ≤ 1 day, M 2–3 days, L 4–5 days)
- **Depends on:** S08.4.1
- **What to do:** Generates test in repo's framework.
- **Done when:** ≥ 60% of generated tests pass validation on benchmark

### S08.4.3 · Approval flow & commit lock test to repo via PR

- **Repo:** backend
- **Size:** M (S ≤ 1 day, M 2–3 days, L 4–5 days)
- **Depends on:** S08.4.2
- **What to do:** Opens PR with test.
- **Done when:** Approved lock appears as PR in customer repo

## Epic context

Scale bug memory from a single module to the whole repo: fingerprinting, lifecycle, automated repro, regression locks for all confirmed bugs and smart lock selection.

Epic acceptance criteria:

- Recurring bugs detected with ≥ 90% precision on benchmark corpus
- Every confirmed+fixed bug gets a validated lock test (fails on buggy commit, passes on fix)
- Relevant locks run on every change in < 5 min p95
